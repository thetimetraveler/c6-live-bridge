How to read a lamp's details

Each lamp is checked three ways, left to right: what Lutron shows, what the bridge last sent, and what the lamp reports (through the Ketra N4 hub, or read directly over Zigbee). Lutron is the reference: it shows the zone level the processor last commanded. Lamp reports reach the processor but don’t change that level, so when a lamp differs from Lutron it is the bridge that is out of step; send the level from Lutron again to line them up.

On the bar, the fill is the lamp, ▼ is Lutron, the thin line is what the bridge sent and ◆ is the show target. K is colour temperature (lower is warmer); vibrancy is Ketra's colour saturation, 0–100.

Readings count as current for 2 minutes through the N4 hub and 7 minutes on direct Zigbee, which reads each lamp after a command and every 5 minutes (every 30 s during a Natural Show). Colour is compared only when both Lutron and the lamp report it.

Activity

Each row is one lighting command and the steps it went through, or a status report or query reply, newest first. Select a row to see every step.

Each step shows who sent it and who received it: Lutron → Bridge Bridge → Ketra hub Ketra hub → Bridge Bridge → Lutron. Reports to Lutron update the processor’s record of the lamp, not the zone level Lutron shows. Step times are measured from when Lutron's command arrived. Asked is the level Lutron requested; Lights is the level the Ketra hub reports the lights are at. Reports without a command association are listed as status updates. Report details separate the report counter from brightness and show why each report was sent. ??? marks a value the bridge couldn't interpret, shown exactly as received.

How commands flow

A lighting command travels left to right along the solid arrows, from the Thread network to the gateway's lighting output: the Ketra N4 hub, or direct Zigbee on gateways built for it. Confirmations and reports travel back along the dashed arrows. Arrows only animate when the gateway reports a real event.

No event outcome is inferred; the flow animates only from observed event records.

    Everyday controls

    Maintenance mode

    Normal operation: lighting control has priority. Mapping changes and firmware uploads require maintenance mode.

    When to use: you rarely need to turn it on yourself: Apply mapping, Apply lamps, Enroll node and the firmware uploads turn it on when they need it. Turn it off when you finish so lighting control resumes at once; it also ends by itself when idle.

    Endpoint control

    Loading

    When to use: to take the endpoint off Lutron's Thread network while you troubleshoot the Lutron system, or to clear a latched safety fault once its cause is fixed. Lighting from Lutron stops while the endpoint is disabled.

    Enable and disable set the gateway's operator choice. Without a physical power switch, disable stops the endpoint's radio in software; it does not cut power and relies on the endpoint firmware honouring the stop.

    Ketra lamps

    Loading

    The lamps direct Zigbee output drives: each Lutron zone's Ketra group and its lamps (Zigbee address and Ketra logical address), with each lamp's live state. Changes need maintenance mode and take effect without a restart.

    When to use: only with direct Zigbee output (or a hybrid gateway): when you set it up, add, replace or re-pair a Ketra lamp, or move a lamp to another Lutron zone. A lamp listed as unreachable or unresolved here is the first thing to check when one lamp misbehaves. N4-only installations don't use it: the N4 hub keeps its own lamp list.

    Edit as JSON

    The gateway's own Ketra address as source, and per zone zone_id, group (pan, logical or null) and lamps (16-hex eui_wire and logical pan, logical, interface, channel, subchannel).

    Import a lab inventory

    Paste a ketra-lab-inventory-v1 file. Zones are matched to the mapping by name; the source address is kept from the editor.

    Zigbee node and firmware

    Zigbee node

    Loading

    The small radio board that talks Zigbee to the Ketra lamps for direct output. The gateway runs its session and re-arms it after every restart; Running is the normal state.

    When to use: Enroll node only once: right after the node's supervised USB install and first join (or after replacing the node board), while it has just started. It is never needed after restarts or firmware updates. If the node shows Record mismatch, find out why (for example a restored or swapped board) before enrolling again.

    Firmware updates

    Two boards take firmware through the gateway. Use the one that matches the file you were given; each checks the file's size before sending.

    Endpoint board (CCX on Thread)

    The C6 that joins Lutron's Thread network and receives commands from the processor. File: an ESP32 app image (.bin, first byte 0xE9), up to 768 KB. Lutron lighting pauses while it restarts; this page watches it come back.

    1. Upload to gateway
    2. Uptime decrease observed
    3. Online again after 30 s

    Zigbee node (Ketra radio)

    The radio board for direct Zigbee output. File: a signed node image, up to 1.5 MB. The node checks the signature, restarts into it and rolls back unless the gateway resumes it. Direct lighting pauses meanwhile; a hybrid gateway uses N4.
